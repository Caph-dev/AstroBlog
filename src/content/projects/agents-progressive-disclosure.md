这个项目很小：一份 `SKILL.md`，一份 `README.md`，加一份七行的配置。功能也只有一件——评估膨胀的 `AGENTS.md`、`CLAUDE.md`，必要时拆成精简的入口文件和按需读取的 `docs/`。

效果我不打算在这里证明。下面只讲一件事：七次提交里，这个技能判断问题的方式换过几轮，以及这些改动各自改变了什么判断。

![agents-progressive-disclosure 的四个阶段：按提交时间排列，每段标注日期、提交哈希、改动内容与判断标准的变化](/assets/images/projects/apd-evolution.png)

## 起点：把一个动作写成步骤

第一个提交 `490a61d`（2026-05-28）一次落地 361 行：README 241 行、SKILL 113 行、配置 7 行。

当时的 `SKILL.md` 是一条直线：

> 识别目标文件 → 检查现有结构 → 把规则分两桶 → 设计 docs map → 重写入口 → 验证规则没丢

「两桶」是硬编码的。语言默认值、安全边界、工具优先级留在入口；命令目录、搜索策略、框架指令、包管理器、环境配置、Git、部署、测试、文档风格，全部下沉。连文档该叫什么名字都写死了——`docs/search-and-evidence.md`、`docs/local-environment.md`、`docs/project-workflow.md`，验证命令也直接是 macOS 配 zsh 的 `wc -l` 和 `rg`。

初版保留了很具体的环境假设：文档名、验证命令、所针对的项目形态都写死在流程里。拿一个刚做成的具体项目当模板，写起来是快，但它描述的是「当时那个项目」，不是「任何项目」。

同一天还有两个只动 README 的提交（`cf60de8` 加 skills.sh 徽章、`2f9fe11` 加社区致谢），各 2 行，主线未变。

## 第一次转向：分类之前，先承认输入可能是矛盾的

`faae6fa`（2026-05-29）在 SKILL 里加 27 行、删 22 行，但真正动的是流程顺序。

最大的改动是在「分类」之前插入了一个新步骤：**先检测矛盾**。风格规则互相打架、包管理器写了两个、测试命令前后不一致、安全边界与优先级声明冲突，或者同一条规则用不同措辞重复了一遍——这些要先扫出来，再依据用户明确指令、最近层级的指令文件或本地证据解决，解决不了才问人。

这一步的位置说明了一件事：矛盾应当先收敛到一处解决。如果输入本身自相矛盾，先分类就可能把同一个冲突分散到不同文档里，反而更难发现。

同一个提交还把模板去具体化了：文档名换成 `[rule cluster]` / `[focused-doc]` 占位符，验证命令从硬编码的 macOS/zsh 改成「按当前环境适配，占位符替换成实际文件」。README 里那串具体文档名也被删掉，换成「保留各平台要求的 frontmatter、imports、path globs」。

这一轮没有增加任何能力，只是把「我以为的默认值」从流程里拆了出去。

## 第二次转向：用删减表达适用边界

一个多月后 `88a0817`（2026-06-30）重写 README，加 90 行、删 149 行；同一天的 `59c6974` 又加 21 行、删 40 行。两次合计净减 78 行。

改写方向是中文优先（原来英文在前），但更值得注意的是文档里第一次出现了**反面结论**：

> 其实将全局 `AGENTS.md` 拆分的必要性并不高，主要是方便维护。省上下文的收益几乎为 0，反正都会命中缓存。
> 但是对于项目级的 `AGENTS.md` 用处就不小了。

这句是当时 README 的判断，没有配套的实测。「缓存命中」也不等于这些指令完全不占上下文，更推不出成本或行为影响接近零。但它确实标出了这个技能的位置：它不是一个通用的「优化手段」，而是一个有明确适用面的工具，主要价值在方便维护。

表达方式也值得记一笔：这条边界是用删减说出来的。同一批提交删掉了「更多安装选项」和「手动安装」的整段，把提醒用 `> [!IMPORTANT]` 和 `> [!CAUTION]` 提到显眼位置，而不是在末尾再加一节「注意事项」。

## 第三次转向：「不拆」变成允许的结论

最近一次 `7ed178f`（2026-11-04）改 SKILL 加 26 行、删 16 行，是四轮里最根本的一次。

技能的目标本身被换掉了。之前是「把长指令文件转成精简入口加聚焦文档」，现在变成：评估这个文件，然后在**保持不动、原地整理、拆分**里选最小的有效改动。这里有个前提——用户没有明确要求拆分；一旦点名要拆，就照做。新增的那一步写得很直白：如果拆分解决不了具体问题（文件本来就不长、规则本来就是配套使用的、收益不清楚），就说明理由然后停下，不备份、不新建文档。默认动作从「拆」变成「先判断」。

分类标准也跟着换了。原来是按主题切：测试的进测试文档，Git 的进 Git 文档。现在要求按**内容本身和使用情境**分，并明确禁止「仅仅因为主题是测试、Git、环境配置就下沉」。判断依据变成两条：这条规则多常用，漏了会怎样。常驻规则和任务细节这两类仍然存在，变的是去向不再由主题单独决定。

验证环节同样在改。旧版包含关键词检查：列一份清单，去新文件里 `rg` 一遍。新版进一步指出这一步的边界——关键词命中只能发现遗漏，不能证明语义还在。所以它保留关键词检查，但增加了对每条被移动或改写规则的比对：力度（must / must not / should）、适用范围、生效时机和例外。

路由表的表头也从「任务类型 / 先读文档 / 触发条件」改成「任务或对象 / 先读文档 / 触发时机」，并加了一条要求：agent 必须能在**不读目标文档的前提下**认出触发条件，并在受该规则约束的动作发生之前去读。

## 这条线说明什么

以上是我对 diff 的解读，不是当初动机的记录。四轮改动里，产品文件始终只有三份：`README.md`、`SKILL.md`，和一份只改过一行的七行配置。没有新增命令、依赖、后台服务或测试框架。

变化集中在两处：

- **判断顺序**：先检矛盾再分类；先判断该不该做再动手。
- **判断标准**：从「这条规则属于什么主题」退到「这条规则什么时候真的会被需要」；从「关键词还在不在」退到「规则还一样硬吗」。

方向是一致的。每一次修正，都在把一个默认前提换成需要论证的条件。

## 还没做完的下一步

本地还有一份未提交的评估草案（`plans/001`）：用 improve 技能对自己的仓库跑了一遍，提出用固定案例来检验这三类决策——保持现状、原地整理、按需拆分各留一个完整示例，再加几个判定依据明确的场景。这些案例尚未在本文中验证。如果它成立，这个项目下一步要解决的就是「怎么判断拆得对不对」，而不是「怎么拆得更多」。
