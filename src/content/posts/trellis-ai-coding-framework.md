# 关于遗忘与秩序：从 vibe coding 到 spec coding 的一次审视

## 序

据说，一旦以 AI 代写代码，人便再难全然回到从前。这种经验，人们称之为 vibe coding：抛出一句需求，其余交由它自行生长。模型既日益强大，于是有人会忘记，此种便利其实奠基于一种深刻的遗忘之上。

当一人唤来 AI 为其书写，他便仿佛置身于一座花园。这座花园每一次都在重新生长。语言在此分岔，如同那位旅人所遭遇的花园——同一件需求，三次对话，便生出三条殊异的路径，彼此镜像，却互不相认。代码的质地于是取决于运数，而非意志。


另一件令人不安的事，是记忆的缺席。每一次新开的会话，都是一场崭新的黎明，而这黎明之前的黑夜，已被彻底抹去。AI 不记得上一次做成了什么，不记得这一隅曾被约定过何种规矩，也不记得方才在若干行注释里重申过的训诫。它只得反复聆听同样的恳求，仿佛一个不断遗忘、却始终耐心如初的生灵。

还有一个更为幽微的病症，是规范之散佚。一座图书馆若缺失了它的目录，便沦为纸张的堆积；一个项目的规矩若散落于评论、讯息与资深者转瞬即逝的记忆之中，则 AI 纵使有力，也无从知晓。它只能依凭自己那一套通用的癖好落笔——而那套癖好，恰恰与一个团队真正的偏嗜背道而驰。

于是，一个判断开始被反复申明：**可被继承的，已非代码，而是规范。** 若将这判断置于更久远的视野里，此言或许近乎谵妄；然在当下，它却正如一面镜子，照见了这一技艺的隐秘脉络。

## 模型与秩序

若要对此种技艺作一分整饬的剖解，可以依循一种古老而天真的分解法：凡一切 agent，皆由两端构成。

其一端是无记忆的理性——理解、推理、而生成。它确然有力。然而另一端，姑且称之为秩序，它决定规范置放于何处，任务之状态如何掌管，上下文如何投喂，经验如何沉淀，工具如何调用，边界如何划定。正是这一端，承载着全部关于过去的事实。

世人之论 AI 编码，常将目光凝于前一层级，仿佛技艺之精粗尽在于此。然凡真正在项目中劳作过的人，皆知其不然：理性再强，也无从知晓数月之前一个团队缘何作此抉择。这些琐细得近乎庄严的「项目事实」，恰恰栖居于秩序那一端。

## 提示词、章程与技能之限

欲约束 AI，人自然而然地想到订立规则。然而单凭其中的某几样，皆各有其明显的疆界。

提示词的病症，在于转瞬即逝。会话一闭，前语尽消，只得从头再述，或令 AI 反溯上一段代码的残影，以揣度其意。此不仅耗费那贵若黄金的 token，更不能保证它当真领会了彼时所立之规范与流程。

`AGENTS.md`、`CLAUDE.md`、`.cursorrules` 诸物，其病症则在于依附于某一特定之物。它们是持久的，一旦写下便长久生效；然 `.cursorrules` 属于 cursor，`CLAUDE.md` 属于 claude code，转用另一工具，便须重新誊写一遍。一队之人，或以此物，或以彼物，各配一套，亦无法于仓廪之中统一掌管。前些时日 claude code 生出一处破绽，诸公司或竟下令禁绝，于是那一套费心经营的项目级约束，便骤然作废。

章程还有一层隐忧：它会随岁月而滋生。新的条目不断添入，旧的条目又无人敢删，终至臃肿不堪。AI 读之，反为所累，抓不住那真正的要害。且章程终究是静态之物——它浑然不知当前的任务，究竟走到了哪一步。

由此观之，问题的焦灼并不在于「要不要规范」，而在于：这规范能否穿越会话、穿越工具、紧随任务而行，既能被反复查验，又能不断更新。若做不到，则它只是一铺沙上的碑铭。

## Trellis 之为物

Trellis 的构想，是将其数物串成一段属于项目的闭环：**spec（规范）、task（任务）、workspace/journal（记忆）、workflow-state（运行之状态）、jsonl（上下文之配置）、finish 与 update-spec（收尾与沉淀）**。

它所关切的，并非此一命令之优劣，亦非彼一 AI 此番能否写出代码。它关切的是：一个项目，能否形成一套可被 AI 读取、可被追溯、且能持续演化的事实之源。质言之，它要让 AI 于新的会话之中，自行寻回「己身之来历、此项目之规矩、昔年止于何处」。

它立下了四个概念，超越平台而恒常：

- **Spec（规范）** `.trellis/spec/`：以 Markdown 书写的编码规约，分门而列（frontend / backend / guides），AI 落笔之前先行阅读。
- **Workspace（工作区）** `.trellis/workspace/`：每位开发者之会话日志（journal），以化解跨会话之遗忘。
- **Task（任务）** `.trellis/tasks/`：工作之单元，内含 PRD、上下文配置与子任务。其生命为：创建 → 规划 → 执行 → 验证 → 归档。
- **Skill（技能）** `.agents/skills/`：自动触发之工作流模块——brainstorm / before-dev / check / update-spec / break-loop。

## 一则需求之一生

将这一切串连起来，一则需求由述说而至收梢，其途大抵如次：

初，新会话苏醒，先恢复项目之上下文；其后每一轮，皆向提示词注入那运行之状态。

继而，判断是否有必要立一 task。若只是叩问一桩技术疑难，或改动甚微，当前对话足以说清，便径直前行，不必劳烦 task。唯有当其涉及多档文件、多番模块、须待设计与复盘之时，它才劝人创一 task。这一点，正是它较 superpowers 令人安适之处——**它并不把万事万物皆化作流程**。

及至 planning，则将一句临时的需求，整理为可以持续推进的任务之资产。譬如人只说「做一个登录功能」，它便要先将「登录失败如何处置、token 如何过期、是否支持第三方、旧用户之数据如何兼容」一一诘问，写入 `prd.md`。于是明日重开一念，AI 便无须自聊天之记录里揣度。

execute 之际，它落笔的依据并非人最后一句嘱咐，而是任务之资产，加以按需所取的相关 spec。spec 不会一次倾尽——依任务所须而择取，较之那份日渐绵长的 rules 文件，更易维护，亦不至令上下文过载。

check 一步，绝非仅仅跑一遍 lint 与 test。它更像一场小型的约章复审——审视 diff，阅读 `check.jsonl` 中所申明的 spec 与 research，再对照规约逐一查验。如接口错误之格式不合于约定、权限之校验偶有疏漏、依赖之方向倒置，诸如此类，test 未必能捕获。

update-spec 之时，则须判断有无值得沉淀之经验。此处易生误会，仿佛任务既毕，AI 便将一切经验尽数写回 spec。实则不然。**spec 若无所不收，终将沦为杂货之冢。** 唯有能长久复用者，方可写入——如「某类接口必当统一错误之格式」「某一模块不得径直依赖另一模块」。至于「登录接口改作 /api/v2/login」一类，留在 task 之中，足矣。

至于 finish-work，则归档任务、书写 journal。须知它**并不为你提交业务代码**——功能之代码先自 commit，它只料理 `.trellis/` 自身的归档与 journal；若有未提交之业务改动，它会峻拒执行。

至此，可将这整段机制凝作一说：Trellis 之落点，已非「AI 能否写出代码」，而是「AI 写代码之际，有无稳定的项目上下文、任务状态、检查标准与收尾机制」。

## 诸种方案之界

若欲为市面诸方案分门别类，可依其设计之偏重，大抵析为四类。其间并无高下，惟取向相殊耳。

其一曰**流程强化型**，superpowers 乃其代表。此家所重者，在 AI 行事之法：先澄清，次立计划，再行 TDD，而后复审。其功，在于能将一袭模糊之念想，梳成可执行的方略，不令 AI 甫一上手便胡乱落笔。然其弊在**重**——细小之事亦反复追问、反复复审，令人不胜其烦。更可叹者，若无项目级之 task / spec / journal 以为根基，则流程既毕，经验仍散落于对话之遗迹中，他日须从头提点。

其二曰**规范管理型**，openspec 属之。此家尊崇 spec-first，先对齐，后实现，凡变更皆缘 proposal、spec、design、tasks 而循序推开。于繁复之需求、悠久之系统，确有裨益。然规范既出，AI 是否每回皆读、是否读得对、是否真个恪守，尚须另设一重法度以兜之；至于任务之状态、工作之记忆、诸平台之适配，亦未必为其所念。

其三曰**多 Agent 编排型**，oh-my-claudecode 可作代表。此家将 planner、executor、reviewer、debugger 拆而分之，使各司其职。然编排之层愈重，agent、skills、hooks 愈多，排查之费辄随之倍增；简单之事强以此法，反成过度之编排。

其四曰**项目闭环型**，Trellis 即其代表。此家把规范、任务、workflow-state、jsonl、journal 与 finish / update-spec 串成一条属于项目之闭环，所念者在于全链路之落地——如何沉淀、如何追踪、如何接续、如何回流、如何令诸异器共奉同一项目之上下文。

## 用之有时，亦有所止

Trellis 虽善，却非无所不包之法器。它所予者，一具工程之骨架而已，并非一劳永逸之自动法。spec 须由人写，须由人更新，须由人清理。

- 若是**一次性之脚本**，譬如油猴之属，径以 vibe 为之可也，不必徒增其繁。
- 若是**无长期维护之价值的项目**，但求其速，则立 task、写 PRD、沉淀经验，反成负累。
- 若是**一方之众不愿维护 spec**，则亦不宜强上。两三人之小队硬要行之，不过留下一堆空模板或过时之规约，愈添其乱。

而于何种情境，则值得用之？项目将长期维护、业务之规矩繁复、多人协作、常换 AI 之器、且愿经验得入仓廪者，是也。

至于使用之费，亦须心中有数：其一，先要明白 `.trellis/` 之下 spec / tasks / workspace / workflow.md / .runtime 各司何职，否则 AI 之所为，观者竟自茫然；其二，须习于 plan / execute / finish 之节律——vibe 是谈罢即书，Trellis 则先澄清、次实现、再查验、终收梢，更稳而更缓，细事而强从重法，体验定然不佳；其三，spec 须时时维护，技术栈变、架构变、规约变，皆当随之而新，过时之 spec 反足误导；其四，task 之颗粒度须加节制，过大则 AI 易迷，过小则又成流程之累——合宜之度，大约系于「此一任务确值得复盘、确涉多档文件或多项抉择、确望他日可续观之」；其五，诸平台之体验颇有参差，官方所涉虽广，而各家 hook、command、sub-agent 之能各异，能接入是一事，体验完备是另一事。

于是可得一简明之判：**短务、小脚本、一己之私役，径行 vibe 可也。** 若有长期之维护、多人之协作、欲经验之入仓，则 Trellis 颇值一试。spec coding 之要，在于沉淀长期有复用之价值的项目事实，而非把万事皆流程化。

## 于一人之值，于一方之值

或谓 spec coding 之必要，惟于团队间见之；一人独处，何须此繁复之构造。然个人之项目经营既久，亦将遭遇同类之劫难：或逾数月复返，则前功尽忘，不知止于何处，遑论缘何作此设计，只得翻检代码与旧谈以自寻；或换掷一时之器，则旧日所配之规约，须一一誊抄他处；或同时维数项之务，其规约各殊，而于同一 agent 之器中往还，AI 辄为上文上下文之习气所牵，偏入歧途；更有甚者，当日令 AI 依一念之快写成之物，隔三月而观，竟不知其所以然——彼时之权衡取舍，惟存于对话之迹，且多经记忆之压缩，无从溯及。

于此可见，spec coding 于一人之实际意义，并非多一套流程，而是令人在行事之际俯身留下必要之文牍，为未来之自己，留一条堪以续接之线。

至于一方之众，其价乃益彰——**一族可不必用同一之器**。昔日因项目规约之存在，不得不令众皆从一器；而 Trellis 则核心跨平台、适配之层各自独立：甲用 cursor，乙用 claude code，新人丙用 codex，而共奉同一套 `.trellis/`。

至于何者可入版本之掌控，其分殊可列如下：**当入 git 者**，为 `.trellis/spec/`（一方之规约，与代码一般经由 PR 复审）、`.trellis/tasks/`（任务之目录，是项目之资产）、`.trellis/workspace/{name}/`（各开发者之 journal）；**当置于 gitignore 者**，为 `.trellis/.developer`（今之开发者名）与 `.trellis/.runtime/`（会话之运行时状态）。

如此，则 spec 与 task 之入 git，即意味着**规约之更易，须如代码一般经由复审**；重要之 API 设计、测试之约、架构之束，一方皆得见、皆得议。而会话级别之暂态，则不劳版本掌控。task 之目录既入 git，或亦有抵牾之虞，故宜以 `--assignee` 明其归属，以免二人共改一役。新人之入，亦得以迅捷上手，交接之事，遂为便利。

## 布置之始

安装与初始化，其事至简：

```bash
npm install -g @mindfoldhq/trellis@latest
cd your-project && trellis init -u your-name
```

初始化之后，宜先将 bootstrap 之任务尽行其事，令 AI 于真实代码之中，抽出一道初版之 spec。否则 `.trellis/spec/` 之内，大抵犹是空模之板，纵使读之，亦无所值。

若用之者为 codex，则须于 `~/.codex/config.toml` 开其 hook，复于 TUI 之中行一遭 `/hooks`，以应允 Trellis 所置之 `UserPromptSubmit` hook。若不为之，则 `/` 之菜单恐不见 Trellis 之令，workflow-state 亦无从自动注入，体验颇有折损。

平日用时，无庸先虑「要不要立一 task」——径于窗口陈其所欲，判之者，Trellis 与 AI 而已；彼问及是否立役时，应之可也。常用之令无过三：`/trellis:start`，惟少数平台须手动启上下文时用之，若有 SessionStart hook 之平台，开终端已自动 orient，平时未必需要；`/trellis:continue`，为最常用者，规划既毕、实现既毕、检查既毕，皆以其推进一步；`/trellis:finish-work`，乃收梢之用，须先 commit 功能之代码，然后行之，它只任归档 task 与书写 journal 之役。

## 结语

vibe coding 自有其价值：写一份脚本，成一件私役，它就是快。然项目一经长期之维护，问题便显其繁复而必要——规范何以保存，任务何以接续，经验何以沉淀，新会话何以不必归零复始。

Trellis 予人之观感，乃是把这些「项目事实」，炼作一套 AI 能读、一族能复审、且可悠悠演化之物。至于用之与否，端视一人之习与项目之境——若只一时之需、细微之务，实无庸迂回辗转。
